객체지향 기본 이론

Value Context vs Identifier Context

Value Context

  • 메모리에 관계없이 값을 관점으로
  • #함수형프로그래밍

Identifier Context

  • 메모리를 관점으로
  • #객체지향프로그래밍
const a = {  
  a: 3,  
  b: 5  
}  
  
const b = {  
  a: 3,  
  b: 5  
}  
  
console.log(a === b); // false (Identifier Context)

console.log(JSON.stringify(a) === JSON.stringify(b)); // true (Value Context)

객체지향 프로그래밍을 할 때 Value Context 를 쓰면 이미 객체지향을 위반하고 있는 것
객체지향에서 그렇다면 값을 쓸때는 언제인가? = 생성자 뿐이다.

Value Context 에서의 특징

1. 끝없는 복사본

  • 값은 메모리값이 중요하지 않다.

2. 상태 변화에 안전?

  • 안전하다. (강제적으로)
  • 3 + 1 = 4 : 3과 1은 그대로 있고 4가 새로이 만들어짐.
  • 계속 불변하는 값을 만들기 때문에 안전해 보일 뿐, 관리하기 어려워짐
  • 이를 관리하기 위해 함수형프로그래밍이 등장

3. 연산을 기반으로 로직을 전개

  • 그림을 그린다는 것을 연상해보자.
  • 복잡한 도메인을 표현하는 연산은 굉장히 어렵다.
Identifier Context 에서의 특징

1. 하나의 원본

  • 상태가 일관성이 없다.

2. 상태 변화를 내부에서 책임짐

  • 내부 상태 상태 관리를 책임지는 객체를 만들어야 한다.

3. 메세지를 기반으로 로직을 전개

  • 객체지향에서는 연산을 통해 문제를 해결하지 않고 메세지(Message) 를 통해 해결
  • 만든 것 까지만 구현하고 다른 객체에게 책임을 위임할 수 있다.

객체지향에서 제일 중요한 것 = 값을 사용하지 않는 것
"값을 못쓰게 하는 것" 만으로 객체지향의 대부분이 달성된다. (마법처럼)

Polymorphism (다형성)

Polymorphism이 뭔지 알아보자.

const Worker = class {  
  run() {  
    console.log('working');  
  }  
  
  print() {  
    this.run();  
  }  
}  
  
const HardWorker = class extends Worker {  
  // 오버라이딩
  run() {  
    console.log('hardWorking');  
  }  
}  
  
const worker = new HardWorker();  

console.log(worker instanceof Worker); // true (Polymorphism)

worker.print(); // hardWorking

대체가능성 (substitution)

console.log(worker instanceof Worker); // true 대체가능성

부모는 자식을 대체할 수 없지만, 자식은 부모를 대처할 수 있다.
자식 부모 말도 안좋다. 집합의 개념으로 받아들이자.

즉, 확장된 클래스는 대상 클래스를 대처할 수 있다. ( #대체가능성 )
확장된 클래스의 부분집합이기 때문.

내적일관성 (internal identity)

worker.print(); // hardWorking 내적일관성

#내적일관성 : 어떠한 경우에도 태어났을 때 원본 클래스를 유지하려는 속성

Ploymorphism = #대체가능성 + #내적일관성

Substitution & Internal identity

Polymorphism ( #다형성 )은 두 가지로 구성되어 있다.

  1. 확장된 객체는 원본으로 대체가능
  2. 생성 시점의 타입이 내부에 일관성 있게 참조됨.

객체지향 언어를 사용한다는 것은 "위 두가지가 지원될거야"라고 믿고 사용하는 것

Polymorphism of Prototype

언어마다 자기만의 방식으로 내적일관성, 대체가능성을 구현한다. 예시를 통해 알아보자.

// 내적일관성 예시 코드
console.log(Object.is(worker.__proto__, HardWorker.prototype)); // true  
console.log(Object.is(HardWorker.prototype.__proto__, Worker.prototype)); // true  
console.log(Object.is(Worker.prototype.__proto__, Object.prototype)); // true
// 대체가능성 예시 코드
console.log(worker instanceof HardWorker); // true  
console.log(worker.__proto__ instanceof Worker); // true  
console.log(worker.__proto__.__proto__ instanceof Object); // true

즉, #JavaScript 는 #prototype 의 #프로토타입체인 통해서 내적일관성, 대체가능성을 유지한다.

JavaScript는 객체지향 언어인가요?

네. 왜냐하면 Polymorphism을 성립하기 때문입니다.

Object essentials

  • 객체지향 언어의 약속이 Polymorphism 이라면, 객체의 책임 무엇인가?
  • 객체지향 언어의 조건을 만족했더라도 객체지향 프로그래밍을 하는 것은 아니다.

"내가 만든 객체가 정상 작동하고, 객체지향 답게 움직인다" 는 본질적인 측면은 무엇인가?
코드를 통해 객체지향의 본질적인 내용에 대해 알아보자.

const EssentialObject = class {  
  #name = "";  
  #screen = null;  
  constructor(name) {  
    this.#name = name;  
  }  
  camouflage() {  
    this.#screen = (Math.random() * 10).toString(16).replace(",", "")  
  }  
  get name() {  
    return this.#screen || this.#name;  
  }  
}

Hide State (데이터 은닉)

const EssentialObject = class {  
	#name = "";  
	#screen = null;
}

속성의 조건은 모두 private이다.

  • 속성이 private이 아니면 객체지향이 아니라고 봐도된다.
  • 객체의 속성을 그대로 보여주면 값으로써 사용된다. (객체지향이 무너진다.)
상태관리 책임 (Maintenance of State)

상태를 내부에서 은닉하여 다루는 것

  • setAge를 통해 외부에 노출하는 것은 내 지갑을 두고 돈을 넣고 빼시오. 하는 격

Encapsulation (캡슐화)

const EssentialObject = class {  
	get name() {  
		return this.#screen || this.#name;  
	}  
}

[!info] #캡슐화 와 #데이터은닉 의 차이점 데이터은닉 : 데이터(field)에 대한 것 캡슐화 : 메소드(method)에 대한 것

위의 예제에서는 camouflage()를 통해 가짜이름을 쓰는지, 진짜 이름을 주는지 외부에서 모른다는 것
즉, 외부에서 내부의 일을 모르게 하는 것

기능의 캡슐화 (Encapsulation of Functionality)

쉽게 생각해서 메소드(method) 는 반드시 캡슐화된 형태로 제공되어야 한다.

속성만 private로 선언하고서 getter, setter 를 통해 날것을 제공하지 마라. 예시 : setAge 를 통해 age 필드를 그대로 노출한 경우

  • 왜 setAge를 하는지 알아야한다.
  • setAge를 그대로 노출했다는 것은 왜? 어떻게 쓸지 고민하지 않았다는 것

객체지향에서는 한단계 더 생각해야지만, 메소드 이름을 정할 수 있다. 예시: setAdult, setChild

  • 이렇게 직접적으로 노출하지 않고 기능에 캡슐화가 가능하다.

Isolation of change

상태관리의 책임(Maintenance of State)
기능의 캡슐화(Encapsulation of Functionality)

객체지향에서 위 두가지를 객체의 본질로 보는 이유

  • 해당 객체의 격리 구간을 만들 수가 있다.
  • 소프트웨어는 변경된다. (PM 욕하지마라.)

변화가 일어났을 때 다른 곳에 변화가 일어나지 않아야한다.

  • 객체지향에서는 격리의벽(데이터은닉, 캡슐화)을 통해 개발한다.
  • 단. 하나의 객체라도 격리의벽이 무너진다면 부수적으로 다른 객체를 변화시키기 때문에 조심해야한다.

알려진 기본 설계요령

#SOLID 원칙

SRP

[!info] #SRP Single Responsibility 단일 책임 원칙
하나의 클래스는 하나의 책임만 가져야 한다.

  • 코드를 고쳐야하는 이유는 하나뿐이어야 한다.
  • SRP를 잘 지키지 못하였을 때 #산탄총수술(Shotgun Surgery)이 일어난다.
    • 산탄총 수술 : 객체 하나를 건드리면 수많은 일이 일어난다.

OCP

[!info] #OCP Open Closed 개방 폐쇄 원칙
확장에는 열려있고 변경에는 닫혀있어야 한다.

  • Open : extends implements 를 할 수 있게끔 만들어야한다.
  • Close : 기존 클래스를 변경하는 것이 아니라 extends implements 로 클래스를 구현해야한다.
    • 핵심은 기존 코드를 건드리지 않는 것
    • 새로운 문제 B를 해결하기 위해, 기존의 문제 A를 해결한 코드에 추가하지 않는 것
    • 새로운 문제 B를 해결하기 위한 새로운 객체에 새로 만들어서 문제를 해결하는 것
    • 기존 문제를 해결하는 A와 B 모두 interface 나 abstract class를 똑같이 상속 받아야 한다. 이 말인즉슨, 문제들의 공통점들을 인식해서 추상화하는 것에 성공했기 때문에 가능한 것

LSP

[!info] #LSP Liskov Substitution 리스코프 치환 원칙 , 업캐스팅 안전
Polymorphism(다형성) 의 대체가능성은 자식클래스는 부모클래스를 대처 가능하다고 하였다.
부모클래스를 대체가능하다는 것은 "업캐스팅이 안전하다."는 의미이다.

  • #업캐스팅 : 부모쪽으로 캐스팅해서 형을 변환하는 것
  • #다운캐스팅 : 자식쪽으로 캐스팅해서 형을 변환하는 것

객체지향으로 작성했다면 Polymorphism을 지킨다는 것인데, LSP는 당연한 것 아닌가요?

추상층의 정의가 너무 구체적이면 구상층의 구현에서 모순이 발생함 = #성급한일반화

예시를 통해 알아보자.

---------------------
추상층
---------------------
- 생물 클래스
	- 메소드
		- 숨을 쉰다.
		- 다리로 이동한다.

---------------------

타조  ok!

아메바 no!

아메바, 독수리, 고래는 부모쪽으로 상속받을 수 없다.
생물이 맞지만 상속받을 수 없다. = LSP 위반

즉, 성급한일반화로 인하여 업캐스팅을 못하게 된 것
어떻게 해결하면 될까?

다리로 이동한다.를 제거하면 모두 해결될 것이다.
하지만 사람, 타조의 다리로 이동한다.기능을 잃게되었다.

독수리(생물) ok!

ISP

[!info] #ISP Interface Segregation 인터페이스 분리 원칙
범용 인터페이스 하나보다는 특정 클라이언트를 위한 여러 개의 인터페이스 분리가 더 좋다

위 예제에서 LSP가 성립하지 않았기 때문에 interface를 분리하였다 = ISP
보다 일반적인 예시를 통해 알아보자.

한 객체에 제공되는 메소드이지만, 사실은 역할에 따라 보면
모듈A,B,C는 모두 서로 기대하는면이 다르다.

이 메소드들은 구분이 되어야된다.

만일 구분이 되지 않아서 객체 자체를 바라보게된다면? 예를들어 만일 중간에 객체가 변경되는 상황이 발생하는 경우 문제가 발생할 것이다. 어떻게 해결할까?

첫 번째 방법

소유, 위임을 사용하여 객체의 분신을 만들어 해결하는 방법

두 번째 방법

객체를 만들 때 용도에 맞게 인터페이스를 정의하여 메소드들을 오버라이드하는 방법
이렇게 하게되면 외부에서 객체를 볼 때는 객체 자체를 보는게 아니라 인터페이스를 통해 인식한다.

정리하면, 객체의 변화가 각각의 모듈 혹은 모듈과 관련된 인터페이스만 영향을 끼치도록 분리 시키는 것이 ISP이다.

DIP

[!info] #DIP Dependency Inversion 의존성 역전 원칙, 다운캐스팅금지
프로그래머는 구체화가 아니라 추상화에 의존해야 한다고 한다.
즉 구현 클래스(구현체)가 아니라 인터페이스(역할)에 의존하라는 이야기이다.
쉽게 이야기해서 의존성은 언제나 부모쪽으로 흘러야한다.

객체지향에서는 절대 다운캐스팅하지 말하야한다.
어떻게 해야 다운캐스팅을 안할 수 있을까??

SOLID 원칙을 잘 지켰을때에만 다운캐스팅을 안할 수 있다.

고차원의 모듈은 저차원의 모듈에 의존하면 안된다.
이 두 모듈 모두 추상화된 것에 의존해야 한다.

추상화된 것은 구체적인 것에 의존하면 안된다.
구체적인 것이 추상화된 것에 의존해야한다.

  • #DI Dependency Injection 의존성주입
    • DI는 #Ioc (Inversion of Control, 제어역전)의 일부이다. 구현체중 하나이다.
  • #DRY Don't Repeat Yourself 중복방지
  • #HolloywoodPrinciple 의존성 부패 방지
    • 요구하지말고 물어보라는 것, 물어보지말고 요청해라.
    • 즉, 액션을 연락하는사람이 거꾸로 연락하게하는 패턴
    • 질의가 되면 안된다.
      • field를 주게된다.
      • 이 패턴을 쓰면 객체지향을 무너뜨린다.
      • 그렇기 때문에 요청해야한다.
        • X : 연락처좀 알려줘
        • O : 시간날때 연락줘
      • 격리의벽을 무너뜨린다.
  • #LawOfDemeter Law of demeter 최소지식
    • 어떤 객체에 대한 지식을 알때, 최소한으로 알아야한다.
    • 그렇지 않으면 의존성 부패가 일어난다.
    • classA.methodA의 최대지식한계 : 최소한의 지식이란 아래 세가지만 알아야한다.
      • methodA의 인자로 넘어온 객체의 타입
        • 예를들어 user.info.age와 같이 안에있는 객체들에 접근하면 안된다. #열차전복 (train wreck)
      • methodA가 생성한 객체의 타입
      • classA의 필드의 타입

  • 설계라는 것은 감각적인 것
    • 어디까지 나눠야하는가?
    • 변화가 더 많이 일어나거나 이유가 많을 것 같으면 상세하게
  • 설계는 상황, 조직을 보고
    • 객체지향에 익숙한 조직인가?

단일 책임 원칙을 준수하는 객체에게 책임 이상의 업무를 부여하면?

  1. 만능 객체가 되려한다. (만능 객체로 작성하면 안된다.)
  2. 다른 객체에게 의뢰한다.

다른 객체에게 의뢰하는 것 = 다른 객체에게 메세지를 보내는 것

책임과 역할을 분리해서 내가할일과 내가할일이 아닌것을 나눠야 진정한 메세지이다.

  1. 메세지 - 의뢰할 내용
  2. 오퍼레이션 - 메세지를 수신할 객체가 제공하는 서비스
    • 어떤 메소드가 처리되는지는 런타임에 결정된다. #동적바인딩
  3. 메소드 - 오퍼레이션이 연결될 실제 처리기

추상 클래스를 상속받게 만들거나 인터페이스를 구현하는 이유
오퍼레이션과 메소드를 분리해서 런타임에 원하는애로 바꾸기 위해서
이런 방식이 OCP를 만들게 된다.

Dependency

의존성의 종류

객체의 생명 주기 전체에 걸친 의존성

  • 상속 (extends)
    • 상속이 안좋은 이유
      • 상속받은 모든 객체가 부모 객체를 건드리는 순간 망가진다.
  • 연관 (association)
    • 필드에 객체타입을 할당하는 것

각 오퍼레이션 실행 시 임시적인 의존성 (약한 의존성)

  • 의존 (dependency)

의존성이 높으면 어떻게 되는가?

  1. 수정 여파 규모증가
  2. 수정하기 어려운 구조 생성
- 수정하기 어려운 구조란 무엇인가?
	- 클래스 내부의 작업은 이해가되지만 어디까지 전파될지 모르기에 겁이난다.
  1. 순환 의존성
  • A를 고쳤는데 B가 망가지는경우
  • 의존성은 단계별로 끊어내지 않으면 한가득으로 문제가발생할 것.

Dependency Inversion

어떠한 경우에도 다운캐스팅은 금지 폴리모피즘 (추상인터페이스) 사용

즉, 다운 캐스팅을 하지말고 항상 추상인터페이스를 사용해라.

const Worker = class {  
  run() {  
    console.log('working')  
  }  
  print() {  
    this.run();  
  }  
}  
  
const HardWorker = class extends Worker {  
  run() {  
    console.log('hardWorking')  
  }  
}
const Manager = class {  
  #workers;  
  
  constructor(...workers) {  
    if (workers.every(w => w instanceof Worker)) {  
      this.#workers = workers;  
    } else {  
      throw 'invalid workers';  
    }  
  }  
  
  doWork() {  
    this.#workers.forEach(w => w.run());  
  }  
}

const manager = new Manager(new Worker(), new HardWorker());  
manager.doWork();

Manager 는 #OCP 를 준수한다.
Worker클래스가 증가해도 Manager 클래스를 변경할 필요가 없다. 즉, 변화에는 닫혀있다.

OCP를 달성하게되면 자연스럽게 의존성 역전이 달성된다.
보다 구체화되어있고 확장된 쪽으로 갖고있지 않고, 보다 추상화된 부분을 갖는다.

코드에서 뭐 의미하고 싶은지가 드러나야한다.

Inversion of Control

#IOC

  • 궁극적으로 도달하고 싶은 범위
  • SOLID 조차도 IOC를 위한 것

제어역전의 개념과 필요성

개념

  1. Control = flow control (흐름제어)
  2. 광의에서 흐름 제어 = 프로그램 실행 통제
  3. 동기흐름제어, 비동기 흐름제어 등

역전이 무슨 말인가?

  • 제어를 안하는 것인가?
  • 역으로 그 일을 대체할 녀석을 만들겠다 와 같은 말
  • 대체하겠다는 의미

문제점

  1. 흐름 제어는 상태와 결합하여 진행됨
  2. 상태 통제와 흐름제어 = 알고리즘
  3. 변화에 취약하고 구현하기도 어려움

대안

  1. 제어를 추상화하고
  2. 개별 제어의 차이점만 외부에서 주입받는다.
const View = class {  
  getElement(data) {  
    throw 'override!'  
  };  
  
  initAni() {  
    throw 'override!'  
  }  
  
  startAni() {  
    throw 'override!'  
  }  
}  
  
const Renderer = class {  
  #view = null;  
  #base = null;  
  
  constructor(baseElement) {  
    this.#base = baseElement;  
  }  
  
  set view(v) {  
    if (v instanceof View) {  
      this.#view = v;  
    } else {  
      throw `invalid view: ${ v }`  
    }  
  }  
  
  render(data) {  
    const base = this.#base;  
    const view = this.#view;  
  
    if (!base || !view) return 'no base or view';  
  
    let target = base.firstElementChild;  
  
    do base.removeChild(target);  
    while (target = target.nextElementSibling);  
  
    base.appendchild(view.getElement(data));  
    view.initAni();  
    view.startAni();  
  }  
}

const renderer = new Renderer(document.body);  
  
renderer.view = new class extends View {  
  #el;  
  
  getElement(data) {  
    this.#el = document.createElement("div")  
    this.#el.innerHTML = `<h2>${ data.title }</h2>`  
    this.#el.style.cssText = `width:100%; background:${ data.background }`  
  }  
  
  initAni() {  
    const style = this.#el.style;  
    style.marginLeft = '100%';  
    style.transition = 'all 0.3s';  
  }  
  
  startAni() {  
    requestAnimationFrame(_ => this.#el.style.marginLeft = 0)  
  }  
}

제어에 대한 부분은 Renerer만 가지고 있다.
추가로 IOC가 되지 않는 것들은 프레임워크라고 부르지 않는다.

제어역전 실제 구현

전략 패턴 & 템플릿 메소드 패턴 < 컴포지트 패턴 < 비지터 패턴
보다 넓은 범위의 제어 역전을 실현함

  • #전략패턴 #템플릿메소드패턴 : 가장 소극적인 제어역전
  • #컴포지트패턴 : 보다 광범위한 범위의 제어역전
  • #비지터패턴

#추상팩토리메소드 패턴 왼쪽 패턴은 이미 만들어진 객체의 행위를 제어역전에 참여시킬 수 있지만 참여할 객체 자체를 생성할 수 없음.
참여할 객체를 상황에 맞게 생성하고 행위까지 위임하기 위해 추상팩토리 메소드를 사용함
