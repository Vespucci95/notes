## MVVM (Model - View - ViewModel)

#MVVM 의 핵심 개념에 대해 알아보자.  
MVVM에 대해 알아보기전에 #MVC 에 대해 먼저 알아보자.

### MVC (Model-View-Controller)

![[Pasted image 20250727183604.png]]

화살표는 누가 무엇을 알고있느냐를 표현한 것.  
컨트롤러는 모델에서 데이터를 가져와 View에게 데이터를 가공해서 전달한다.  

```txt
- View는 유저의 인터렉션을 받아 모델을 갱신한다. 
- View는 어떤 Model을 갱신해야하는지 알고있다.
- View가 Model을 알고있는게 무엇이 문제일까?  
- 이게 가장 큰 문제를 일으킨다 .  
- 모델은 비즈니스 도메인에 관련된 내용이다.  
- 뷰는 화면이 이쁘냐 안이쁘냐 이런것에 관심이 있고 유저 인터렉션과 관련된 부분을 담당한다.
- 여기서 뷰와 모델이 알고있다는 것이 MVC의 약점이다.  
- MVC는 백엔드에서 주로 선호한다.  
```

프론트엔드에서는 양방향으로 흐르기떄문에 MVC가 적합하지 않다.  
Model의 변경이 View의 변경을 간접적으로 야기하기 때문

### 제왕적 MVC

![[Pasted image 20250727185359.png]]

```txt
- 컨트롤러가 왕이다.
- 컨트롤러가 뷰와 모델을 모두 알고 있다.
- 모델이나 뷰의 변경이 일어난다면 컨트롤러의 변화가 생긴다. (비대해진다)
- 컨트롤러에 대한 의존성이 굉장히 심하기 때문에 유지보수가 어려워진다.
```

### MVP (Model-View-Presenter)

![[Pasted image 20250727185424.png]]

```txt
- View의 getter, setter가 노출되어 있다.
- View에는 순수한 getter, setter만 존재한다.
- Presenter에서 View에서 getter, setter를 통해 컨트롤 한다.
- View하나를 만들기위해 getter, setter를 만들어야한다.
- MVP를 하게되면 하나의 View를 만들때마다 getter, setter를 작성해야한다. (부담)
```

### MVVM (Model-View-ViewModel)

![[Pasted image 20250727190150.png]]

```txt
- MVVM이 성립하기 위해서는 `Binder`가 있어야 한다. 그렇지 않으면 성립하지 않는다.
- Binder가 없으면 많은 문제가 해결되지 않는다.

- 핵심적으로 알아야할 ViewModel
- ViewModel이 뭔데? = 순수한 View라고 볼 수 있다.
- 진짜 그대로의 View가 아니라 순수한 데이터로서의 View
- 즉 DOM을 다루지 않는다.

- ViewModel을 가지고 실제 View와 Binder가 자동으로 ViewModel의 변화를 감지해서 View에 반영되기를 바라거나
- View의 변화를 Binder를 타고 ViewModel을 갱신하거나,
- 즉 이 과정을 자동화해주는 Binder가 없으면 화면의 갱신이 이러나지 않을 것.
- 이때문에 Binder가 없으면 MVVM이 성립하지 않는다고 이야기한 것
- Binder가 View와 ViewModel의 의존성을 없애주는 역할을 한다.


- 두번째 핵심
- ViewModel은 View를 모른다.
- ViewModel은 View를 알고있으면 MVVM이 아니다.
- 양방향 바인딩이란 observe가 어디에 걸려있느냐의 차이

```

## TypeCheck

const type = (target, type) => {  
  if(typeof type === 'string') {  
    if(typeof target != type) {  
      throw `invalid type ${target} : ${type}`  
    }  
  } else if (!(target instanceof type)) {  
    throw `invalid type ${target} : ${target}`  
  }  
  return target;  
}

## View hook & bind

View에는 어떤 ViewModel과 매칭할지에 대한 별도의 hook이 필요하다.

```html
<section id="target" data-viewmodel="wrapper">
	<h2 data-viewmodel="title"></h2>
	<section data-viewmodel="contents"></section>
</section>
```


여기서는 [`data-*`](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/Use_data_attributes) 를 사용하여 `wrapper`, `title`, `contents` 라는 hook을 추가한다.  
이후 binder를 통해 ViewModel의 속성과 일치하는 녀석들을 매핑한다.   
ViewModel에는 `wrapper`, `title`, `contents`과같이 hook과 매칭되는 녀석들이 있을 것이다.

## Role Desgin

MVVM의 핵심은 Binder에 있다.  
Binder가 없는 MVVM은 없다.

두 가지 방식이 있는데 Vue.js, Angular 에서 태그를 scan 하게 만드는 것과,  
데이터와 연결되어있는 View를 만들어서 이 View를 뽑아내는 방식 (React)

두 가지 방식의 장단점

첫 번째 방식 (Vue, Angular)
- Model과 View를 분리해서 관리하기가 쉽다.
두 번째 방식 (React)
- property, state, view가 공존한다. (컴포넌트)

![[Pasted image 20250803183350.png]]

Binder와 ViewModel을 알고 있다. 알아야지 그림을 그릴 수 있기 때문  
그런데, HEMLElement 를 직접적으로 알게할 것이냐?  
알게하면 HTML에 있는 scan정보를 하드코딩하게 된다.  

Binder가 HTML을 인식하는 부분을 빼기위해서 Scanner를 따로 둔다.  
Scanner를 따로두는 이유는 변화율 때문이다.

변화율이란 코드를 얼마나 자주 수정하는 부분이아니라  
**코드를 바꾸는 이유가 똑같은지 아닌지에대한 이야기**이다.
- Binder는 ViewModel을 이용해서 View를 그릴때한 로직을 바꿀 때
- 즉, 원인에 따른 변화율

Scanner의 존재 이유는 Binder와 HTMLElement의 직접적인 연관을 끊어내기 위한 것  
Scanner를 둠으로 써 HTML 변화에 따른 Bidner의 변화율을 막아낼 수 있다.

## ViewModel

ViewModel에 대해 알아보자.  
순수한 인메모리 객체이기 때문에 ViewModel을 작성하기 쉽다.

```js
const ViewModel = class {  
  static #private = Symbol();  
  
  static get(data) {  
    return new ViewModel(this.#private, data);  
  }  
  
  styles = {};  
  attribute = {};  
  properties = {};  
  events = {};  
  
  constructor(checker, data) {  
    if (checker != ViewModel.#private) throw 'use ViewModel.get()!'  
    Object  
      .entries(data)  
      .forEach(([k, v]) => {  
        switch (k) {  
          case 'styles':  
            this.styles = v;  
            break;  
          case 'attribute':  
            this.attribute = v;  
            break;  
          case 'properties':  
            this.properties = v;  
            break;  
          case 'events':  
            this.events = v;  
            break;  
          default:  
            this[k] = v;  
        }  
      })  
  
    Object.seal(this);  
  }  
}
```

ViewModel의 장점은 단위테스트를 짜기가 쉬워진다.  
Binder가 핵심인 이유는 화면을 그리는 복잡한 로직은 Binder가 가져갔다. ( #IOC , 제어 역전 )  

## Binder

```js
const BinderItem = class {  
  el;  
  viewmodel;  
  
  constructor(el, viewmodel, _0 = type(el, HTMLElement), _1 = type(viewmodel, 'string')) {  
    this.el = el;  
    this.viewmodel = viewmodel;  
    Object.freeze(this);  
  }  
}
```

사용은 아래와 같이 사용한다.

```html
<section id="target" data-viewmodel="wrapper">
	<h2 data-viewmodel="title"></h2>
	<section data-viewmodel="contents"></section>
</section>
```

```js
new BinderItem(section, 'wrapper');  
new BinderItem(h2, 'title');  
new BinderItem(section2, 'contents');
```

Binder는 아래와 같이 구현한다.

```js
const Binder = class {  
  #items = new Set;  
  
  add(v, _ = type(v, BinderItem)) {  
    this.#items.add(v);  
  }  
  
  render(viewmodel, _ = type(viewmodel, ViewModel)) {  
    this.#items.forEach(item => {  
      const vm = type(viewmodel[item.viewmodel], ViewModel)  
      const el = item.el;  
  
      Object  
        .entries(vm.styles)  
        .forEach(([k, v]) => el.style[k] = v)  
      Object  
        .entries(vm.attribute)  
        .forEach(([k, v]) => el.setAttribute(k, v))  
      Object  
        .entries(vm.properties)  
        .forEach(([k, v]) => el[k] = v)  
      Object  
        .entries(vm.events)  
        .forEach(([k, v]) => el['on' + k] = e => v.call(el, e, viewmodel))  
    })  
  }  
}
```

## Scanner

```js
const Scanner = class {  
  scan(el, _ = type(el, HTMLElement)) {  
    const binder = new Binder;  
    this.checkItem(binder, el);  
  
    const stack = [el.firstElementChild];  
    let target;  
    while (target = stack.pop()) {  
      if (target.firstElementChild) stack.push(target.firstElementChild);  
      if (target.nextElementSibling) stack.push(target.nextElementSibling);  
    }  
  
    return binder;  
  }  
  
  checkItem(binder, el) {  
    const vm = el.getAttribute("data-viewmodel");  
    if (vm) {  
      binder.add(new BinderItem(el, vm))  
    }  
  }  
}
```

정리하면, MVVM 이라는 객체 구조를 이해하는게 객체를 관리하는 것에 도움이 된다.

- Model이 바뀔때마다 View가 영향을 받는 의존성 문제
- View마다 View를 만들어줘야하는 로직을 MVC에서 하나씩 만들어야하는 문제들
	- 제어역전을 통해서 해결
	- View를 직접적으로 알지 못하게함.
