## Strategy Pattern 전략 패턴

Strategy는 전략이라고 표현하기보다는 알고리즘 혹은 도메인 이라고 표현할 수 있다.  
즉, 어떤 문제를 해결하기위한 핵심적인 지식 부분을 의미한다.

[[2회차]]에서 작성하였던 Binder를 다시 살펴보자.

```js
const Binder = class {  
  #items = new Set;  
  
  add(v, _ = type(v, BinderItem)) {  
    this.#items.add(v);  
  }  
  
  render(viewmodel, _ = type(viewmodel, ViewModel)) {  
    this.#items.forEach(item => {  
      const vm = type(viewmodel[item.viewmodel], ViewModel)  
      const el = item.el;  
  
      Object  
        .entries(vm.styles)  
        .forEach(([k, v]) => el.style[k] = v)  
      Object  
        .entries(vm.attribute)  
        .forEach(([k, v]) => el.setAttribute(k, v))  
      Object  
        .entries(vm.properties)  
        .forEach(([k, v]) => el[k] = v)  
      Object  
        .entries(vm.events)  
        .forEach(([k, v]) => el['on' + k] = e => v.call(el, e, viewmodel))  
    })  
  }  
}
```

이 코드가 전체 하나의 덩어리로 보이겠지만 사실 그렇지 않다.  
`Structure(자료구조) & Control(제어)`의 코드가 혼합되어 있다.

위 부분들은 전략에 대한 부분이 아니다.


Strategy는 처음부터 Structure를 가지고 사용할 수 있다.  
객체지향에서는 이런 문제를 해결하기위해 Composition을 사용한다.  
Composition은 code 를 object(객체)로 변경한다.  

> [!question] 왜 object로 변경하는가?
> - 변경하기위해서는 코드를 고쳐야한다.
> - 코드를 고치면 모두 회귀 테스트를 해야한다. 코드가 변경되었기 때문
> - 객체로 변경하면 공급되는 객체만 바꾸면 된다.

객체를 도출할 때 `interface` 나 `class`로 도출해야한다.  
즉 `type`을 정의해서 객체를 받아들이면, 기존 코드에는 없었던 #Dependency (의존성)이 생기게 된다.  

> [!question] 객체지향에서 Dependency가 발생하는 이유는?
> - 위임했기 때문이 아니라 나의 Strategy를 외부에 있는 객체의 도움으로 해결하기 위해
> - 외부 객체의 도움을 받지 않는다면?
> 	- 변화가 생길때마다 코드를 고쳐야한다.
> 	- 하드코딩
### DI (Dependency Injection)

객체지향에서는 code를 object(객체로) 빼내는 순간 Dependency와 Dependency Inject ( #DI) 가 자동으로 생기게된다.  
객체에 대한 의존성을 내부에서 생성하면 Dependecny만 생긴다.  
이렇게 처리할 경우 code를 object로 변경할 의미가 없다. 이유는 위의 내용과 같다.  
내부에 Dependency가 생긴 경우 그냥 code로 관리하는 것이 나을 수 있다.  

따라서 외부에서 type을 Injection(주입) 받아야한다.  
Dependency가 있는데 Injection이 들어오고 있지 않다면 잘못된 것이다.

```js
const Processor = class {  
  process(vm, el, k, v, _0 = type(vm, ViewModel), _1 = type(el, HTMLElement), _2 = type(k, "string")) {  
    this._process(vm, el, k, v)  
  }  
  
  _process(vm, el, k, v) {  
    throw "override"  
  }  
}
```

`process`는 내부에서 직접처리하지 않고 `_process`에 위임하고 있다.  
따라서 이 composition은 부모와 자식사이에서 일어난다.  

DI 방향을 두 가지로 설정할 수 있다.
- 외부에서 공급받는 방법
- 내부에서 자식한테 위임하는 방법 ( #템플릿메소드패턴 #TemplateMethod )
	- 외부에서는 process로 보이지만, 내부에서는 자식쪽으로 주입되어있는 method에 의존하고 있다.
	- 자식쪽에 의존하고 있는 method를 Template Method Pattern에서는 hook 이라고 한다.

이제 Processor를 적용하기 위해 Binder를 수정한다. 전체 코드는 아래와 같다.

```js
const Binder = class {  
  #items = new Set;  
  #processors = {};  
  
  add(v, _ = type(v, BinderItem)) {  
    this.#items.add(v);  
  }

  // 전략을 주입
  addProcessor(v, _0 = type(v, Processor)) {
	/**  
	 * 여기서는 Value Context가 사용되었다.  
	 * Identifier Context를 사용하지 않는다면 안전하게 처리하기 위한 추가 로직이 필요할 것.  
	 */
    this.#processors[v.category] = v;
  }  
  
  render(videmodel, _ = type(videmodel, ViewModel)) {  
    const processores = Object.entries(this.#processors);  
    this.#items.forEach(item => {  
      const vm = type(viewmodel[item.viewmodel], ViewModel)  
      const el = item.el;  
      processores.forEach(([pk, processor]) => {  
        Object.entries(vm[pk]).forEach(([k, v]) => {  
          processor.process(vm, el, k, v);  
        })  
      })  
    })  
  }  
}  
  
const Processor = class {  
  category;  
  
  constructor(category) {  
    this.category = category;  
    Object.freeze(this);  
  }  
  
  process(vm, el, k, v, _0 = type(vm, ViewModel), _1 = type(el, HTMLElement), _2 = type(k, "string")) {  
    this._process(vm, el, k, v)  
  }  
  
  _process(vm, el, k, v) {  
    throw "override"  
  }  
}
```

>[!question] 알고리즘의 일반화, 알고리즘의 추상화, 제네릭 알고리즘
>공통 로직을 묶어냈다. 제네릭 사용했다. 이런 문제가 아니다.
>
>1. 나의 복잡한 코드들의 공통점을 객체로 분리
>2. 객체를 형(type, interface, class)으로 분리
>3. 형에 맞는 알고리즘을 작성하고 그 객체가 제공하는 method만 사용하여 풀어내는 것

사용은 아래와 같이 한다.

```js
const binder = scanner.scan(document.querySelector("#target"));  
binder.addProcessor(  
  new (class extends Processor {  
    _process(vm, el, k, v) {  
      el.style[k] = v;  
    }  
  })('styles')  
)  
  
binder.addProcessor(  
  new (class extends Processor {  
    _process(vm, el, k, v) {  
      el.setAttribute(k, v);  
    }  
  })('attributes')  
)  
  
binder.addProcessor(  
  new (class extends Processor {  
    _process(vm, el, k, v) {  
      el[k] = v;  
    }  
  })('properties')  
)  
  
binder.addProcessor(  
  new (class extends Processor {  
    _process(vm, el, k, v) {  
      el['on' + k] = e => v.call(el, e, vm);  
    }  
  })('events')  
)
```

binder가 processor를 의존하게 되었다.  
위에서 이야기하였듯이 Dependency가 생겼으면 Dependency Injection이 생기게 되었다.

옵저버 패턴은 감시당하는 쪽에서 감시하는쪽으로 notify를 준다.
- 감시하는 쪽 (Observer, 옵저버)
- 감시당하는 쪽 (Subject, 주체)

Subject는 자신이 변경되었다는 것을 알기가 힘들다.
ViewModel은 순수한 인-메모리 객체라고 하였다. 객체의 속성이 변하는 것을 어떻게 알 것인가?

JS에서는 이 부분에 대해서 두 가지 방법을 지원한다.
- `defineProperty`
	- 실무상에서 쓸 수 있다.
- `Proxy`
	- es6 이후부터 지원 
	- babel로 컨버팅이 되지 않는다.

## Listener

옵저버에서 수행할 애들은 형으로 정의한다.  

```js
const ViewModelListener = class {  
  viewmodelUpdated(update) {  
    throw 'override'  
  }  
}
```

기존의 ViewModel 에 다음과 같이 추가한다.

```js
const ViewModel = class extends ViewModelListener {  
  static #private = Symbol();  
  
  static get(data) {  
    return new ViewModel(this.#private, data);  
  }  
  
  styles = {};  
  attribute = {};  
  properties = {};  
  events = {};  
  
  #isUpdated = new Set;  
  #listeners = new Set;  
  
  addListener(v, _ = type(v, ViewModelListener)) {  
    this.#listeners.add(v);  
  }  
  
  removeListener(v, _ = type(v, ViewModelListener)) {  
    this.#listeners.delete(v);  
  }  
  
  notify() {  
    this.#listeners.forEach(v => v.viewmodelUpdated(this.#isUpdated));  
  }  
  
  constructor(checker, data) {  
    super();  
    if (checker != ViewModel.#private) throw 'use ViewModel.get()!'  
    Object  
      .entries(data)  
      .forEach(([key, obj]) => {  
        if ("styles,attributes,properties".includes(key)) {  
          this[key] = Object.defineProperties(  
            obj,  
            Object  
              .entries(obj)  
              .reduce((r, [k, v]) => {  
                r[k] = {  
                  enumerable: true,  
                  get: _ => v,  
                  set: newV => {  
                    v = newV;  
                    v.#isUpdated.add(new ViewModelListener(category, k, v));  
                  }  
                }  
                return r;  
              }, {})  
          );  
        } else {  
          Object.defineProperty(this, key, {  
            enumerable: true,  
            get: _ => obj,  
            set: newV => {  
              obj = newV;  
              this.#isUpdated.add(new ViewModel("", key, obj));  
            }  
          })  
        }  
      })  
  
    Object.seal(this);  
  }  
}
```

소유하고 있는 ViewModel안에 어떠한 프로퍼티가 변해도 isUpdated의 set에 계속해서 추가하는 식이다.

## Composite Pattern

내가 내문제를 동일한 문제임에도 불구하고 위임을 반복해서 취합하는 행위  

Binder는 최상위의 ViewModel을 구독한다.  
최상위의 ViewModel의 변화가 생겼을 때 하위 ViewModel에도 알려야 한다.  
즉, 부모 ViewModel 과 자식 ViewModel간의 Observer를 구성한다.  
부모가 observer가 되고 자식이 subject가 되는 형식이다.
이런 구조를 Composite Pattern을 통해 해결한다.
